# Changelog

## [Unreleased]

### Removed
- **The cross-encoder reranker hook.** `vectorstore.Reranker`, `HTTPReranker`, `MemoryStore.SetReranker` and the rerank step in `Search` were never wired to a flag or a server, so nothing could turn them on. Near-duplicate collapse and the state-aware re-rank are unchanged. A handful of unreachable helpers went with it (the `ReadSnapshot*From` wrappers, `NewReadToolsServer`, Azure's duplicate `handleLogout`).

## [2.2.0] - 2026-10-25

### Fixed
- **With sign-in off (`--dev`) the server has a user.** Every request without a session is the built-in user `dev`, a real session, so voice, personal notes, the live event stream, `/v1/auth/me` and the UI see one identity. Before, voice saved notes under the key of an empty ID, which the notes list and the event stream refused to serve, and the UI skipped notes for an anonymous caller. Behind a sign-in provider nothing changes. The voice `search_memory` also searches a user's private notes with the ranked search (keywords, then meaning) instead of keywords alone, and `list_memory` includes them.
- **A voice session opens knowing the user's past.** The system prompt now carries the user's newest private notes (ten) and session memories (three), one line each, so the model starts with what it saved before instead of having to guess to search.

### Removed
- **The `xray-graph` chart.** The repository publishes one chart, `xray` (ADR-060). A map loads into the memory server from one `mental_map` cell (`data.graphRef`), so the standalone snapshot-server deployment is not needed to serve one. `xray graph serve-snapshots` is still in the image for a standalone snapshot server.

### Changed
- **The API group is `xray.triageagent.dev`** (ADR-059), not `xray.ai`: `apiVersion: xray.triageagent.dev/v1`, the CRD `memorycells.xray.triageagent.dev`, the cell labels and the chart's RBAC. Breaking and without a conversion: an existing install applies the new CRD (Helm installs `crds/` only on a first install) and copies its cells across, changing `apiVersion`. The Triage core shares the type, so a deployment that runs both moves both.
- **The default Gemini Live model is `gemini-3.8-live`** (the `--voice-model` default and the chart's `systemConfig.voiceModel`; it was `google/gemini-live-2.5-flash-native-audio`). The `system_configuration` cell still overrides it per session. On Vertex it is served only on the multi-regions `eu` and `us`, so run voice there with the new `--voice-location` (default: `--gcp-location`, which keeps the embeddings location). Affective dialog is not sent to a Gemini 3 model, which closes the session when it is set. The genai SDK moves from v1.45 to v1.72, the version that reaches the multi-region endpoints.

### Fixed
- **A voice question could loop through dozens of tool calls.** A model asking for a File node got an empty string and asked again, about twenty times in one session: 82 model turns and 823k input tokens, because each round trip re-reads the whole conversation. A `get_graph_node` on a file now lists the file's symbols with the qn to fetch each by; a code-graph call repeated verbatim in a session is answered once and then refused with a pointer to the earlier result; and a model turn is capped at 6 tool calls and a session at 40 (the Triage core's numbers), after which the model is told to answer from what it has.
- **Voice transcript bubbles are one per speaker turn.** The UI made a bubble per chunk and removed each six seconds after it appeared, which left a column of fragments that could not be read. Chunks now extend the speaker's current bubble, which leaves eight seconds after its last chunk.
- **`end_session` is answered by hanging up, not by a tool response.** A response gives the model one more turn and it fills it with speech: given a bare status it read the status out after the goodbye, given an instruction to stay quiet it said so aloud. The call now goes unanswered and the session closes after the drain window that lets the goodbye finish playing, as in the Triage core. The tool description asks for the goodbye first and nothing after.
- **Latency histograms have second-sized buckets.** The OpenTelemetry defaults (0, 5, 10, 25 ...) put every time to first token, tool call and search into the first two buckets. A `voice first audio` log line gives each turn's time to first audio and the tool calls that came before it.

### Added
- **A `mental_map` cell can point at its graph in a registry.** `spec.data.graphRef` holds a digest-pinned OCI reference (plain text; `name@sha256:...`), the memory server pulls the artifact, takes its one `*.graph.gob.gz` file (a `make maps-image` image qualifies; an age-encrypted snapshot opens with `--mental-maps-snapshot-key`) and registers it as a map, so one deployment answers `search_memory` and the code-graph tools, in MCP and by voice. The same key and shape the Triage core reads. It pulls once per reference, retries every 30 s while the registry is unreachable, and refuses a tag. New `--registry-pull-secret` names a dockerconfigjson Secret for a private registry. Needs `--mental-maps-dir` (it may be empty) and the embedder the map was built with.
- **Kotlin and Swift in the code graph.** `.kt`, `.kts` and `.swift` files go through the generic tags extractor, so classes, objects, protocols, functions and calls are searchable. The Kotlin grammar ships no tags query; ours is `queries/kotlin.scm`. Swift uses the grammar's own, plus call references. Swift comes from the grammar's `with-generated-files` branch (its parser is a 23 MB generated C file, so the CGO build compiles it once and caches it).
- **`--otel-token-secret`**: a Secret (key `token`) whose value is sent as a bearer header with every OTLP trace export, so traces can go to a collector that requires one, such as ego. The token is read from the cluster once the cache syncs and follows later changes. The chart's tracing example now names gRPC port 4317 (it said 4318, the HTTP port).

## [2.0.0] - 2026-10-24

### Removed
- **The `mentalMaps` chart values and the `mental_map` cells they wrote.** The chart mounts no map volumes, so the cells described a mount that did not exist. Maps arrive as cells that carry a graph, or as files in `--mental-maps-dir`; image volumes are the `xray-graph` chart.
- **`xray recall` and the `xray-recall` chart**, replaced by `xray graph` and `xray-graph`. The `Dockerfile.baked` variant and the per-repo source image target went with them.
- **The reflection/knowledge memory loop.** X-Ray is the memory substrate only; consolidation belongs to the agent that uses it. Removed: `ReflectionManager` and its LLM client, the flags `--reflection-model`, `--reflection-interval`, `--knowledge-interval` and `--reflection-event-threshold`, the MCP tools `build_memory` and `build_knowledge`, the `summary` field of `get_memory` and of the voice orientation tool, the knowledge digest appended to the voice system prompt, the reflection trigger at the end of a voice session, the chart's `reflection:` values and the matching `args`, and ADR-021 with its todos.
  - **Kept**: the deterministic retention sweep and the episodic reaper (TTL deletes, no model calls).

### Added
- **The web UI is part of the binary** (ADR-055). The memory graph, search, per-kind lists, voice and the live view of recalls, previously a separate repository, are in `ui/` and embedded in `xray`, which serves them at `/` on the same origin as the API. `make run` opens it on :8080; the chart serves it through the same Service. It speaks X-Ray's own `/v1` API (voice, server-sent events, per-user notes) and builds for a Triage deployment's `/v2` with `NEXT_PUBLIC_API_PREFIX=/v2`. Each document gets a CSP naming the hashes of its own inline scripts. New `--ui` flag (default on); `make build UI=0` builds without the UI and without Node; `make ui`, `make ui-dev` and `make ui-test`. The release workflow builds the UI before ko compiles it in.
- **The recall effect in the UI**: a blue fibre lights the recalled region, its cells fire in the order the light reaches them, the recalled cells fire hardest, and a pulse runs along their links (see the README).
- **A recall over MCP lights the UI.** `search_memory` now publishes a hit event naming the shared items it returned, with their kinds, as the voice tools and `get_memory_context` already did. Private items are never named on the stream. The README and the specification explain how a hit becomes the optogenetic effect in the web UI, with a looping figure (`docs/img/recall.svg`).
- **X-Ray as a library, in the caller's process.** `pkg/memory` is the memory store (typed items, keyword and trigram index, HNSW over embeddings, write dedup, recall shaping, provenance), with `WithEmbeddings`, `WithFile` (loaded on open, rewritten after every change), `WithOrigin`. `pkg/codegraph` is the code graph: `Build` and `UpdateGraph` parse with Tree-sitter (cgo), `Save` and `Load` use the snapshot format the server reads, `Handler` serves it over MCP, and a build without cgo can still `Load` and search (`ErrNoParser` from `Build`). `*memory.Store` and `*xray.Client` implement the new `xray.Memory`; `*codegraph.Graph` and `*xray.Client` implement `xray.CodeGraph`, so an agent runs on either. `examples/agent` and `adapters/adk` run over an embedded store as well as a client.
- **Google ADK adapter** (`adapters/adk`, its own module): `xrayadk.New` is an ADK `memory.Service` backed by X-Ray, so it plugs into the runner and the stock `preload_memory` and `load_memory` tools; `SaveTool` and `RefuteTool` give the model write access. `examples/agent` is a provider-neutral agent loop with X-Ray as its memory. See `docs/sdk.md`.
- **Go SDK** (`github.com/triageagent-dev/x-ray/v2/pkg/xray`): a typed client over MCP for authored memory (`Search`, `Upsert`, `Refute`, `Supersede`, `Context`, ...), the code graph (`SearchGraph`, `Node`, `Impact`, `Risk`, ...) and agent notes (`Remember`, `Recall`, `Forget`), with `Call` for any other tool. Server refusals are `*ToolError`. The tests run the SDK against the real memory MCP server.
- **The code graph is part of the product** (ADR-054). `xray graph <sub>` replaces `xray recall`: `serve`, `snapshot`, `serve-snapshots`, `servicemap`, `dump`, `update`, `status`, `build`, `install`, and new `search`, `impact`, `services`, `keygen`, `version`. The packages are the standalone `xray-memory` project's, under `internal/codegraph`, so X-Ray gains:
  - **Encrypted snapshots** (age): builders take a recipient, servers an identity. The memory server opens them with `--mental-maps-snapshot-key` (or `$XRAY_SNAPSHOT_KEY`).
  - **Agent notes**: `remember`, `recall` and `forget` over a notes map, with expiry.
  - **Access control for the local graph server**: loopback by default, Host and Origin checks, optional bearer token.
  - **More extractors**: Compose files, Dockerfiles, application config and SQL DDL feed the service map.
  - `get_graph_risk` and `list_skills`/`get_skill`.
- **`imagePullSecrets`** in the `xray` chart, for installs from a private registry.
- **`xray-graph` chart**, the standalone snapshot server (image volumes or a seeded volume, auth, age identity, HPA, ingress).
- **OCI publishing.** Each release pushes `ghcr.io/triageagent-dev/xray:<version>`, the parser build as `:<version>-parser`, and the charts `xray` and `xray-graph` to `oci://ghcr.io/triageagent-dev/charts`.
- **`expire_memory`, `supersede_memory` and `get_memory_context`** (MCP). Expire retires an out-of-date item (status `stale`). Supersede writes a replacement that lists the old id in `supersedes` and retires the old item (`superseded`); a derived replacement cannot supersede a human item. Context follows ThoughtLinks from an anchor (an id, a subject, part of a title) with activation decaying 0.6 per hop times link weight, depth 3 by default, 8 at most, shared cells only.
- **Writing rules.** An upsert through MCP or voice needs a kind from the vocabulary and `confidence=high` on a `stable_fact`; a kind filter on search or list must name a searchable kind, so a mistyped one is an error and not an empty result. `hypothesis` and `unknown` now decay by default (24 hours, 7 days), and a merged restatement renews them.
- **Cells written elsewhere are followed.** A cell another replica (or `kubectl`) creates, edits, retires or deletes updates this pod's keyword and vector indexes and is announced to its live clients as a change; the pod's own writes are recognised and not announced twice. Search-hit pulses stay per pod.
- **`xray.memory.search.phase.duration`**: the embed and index phases of a semantic search, separately.
- **Cell provenance: `spec.origin`** (`observed`, `derived`, `human`, `verified`; unset reads as derived). A write is human when its credential names a person (an OAuth-issued MCP token, a signed-in voice session) and derived otherwise; the server never takes an origin from the caller. A derived write cannot replace a human cell. `upsert_memory` takes `evidence_refs`. Items in REST and MCP results carry `origin`, `evidenceRefs` and `supersedes`.
- **`refute_memory`** (MCP, write scope): retires a cell that is wrong (status `stale`), records reason and evidence under `data.refuted`, and retires every active derived cell that cites it by evidence ref or link, one hop. `Persist` now stores a stale or superseded status instead of resetting it to active.
- **`consolidate_memory`** (MCP, write scope): reports near-duplicate `stable_fact`, `operational_pattern`, `watch_item` and `hypothesis` clusters (keeper, restatements, scores); with `apply` retires the restatements as `superseded`.
- **Write-side dedup** (`--memory-write-dedup`, default on): an upsert that restates one of those four kinds lands on the cell it repeats (status `merged`, `merged_into` in the MCP reply, tags unioned). Cells must share kind, scope and subject; a model-written restatement is not merged into a human cell. A short token that carries a digit counts toward similarity, so "Q3 plan" and "Q4 plan" stay two cells.
- **Recall shaping** (`--search-recall-shaping`, default on): near-duplicate facts collapse to the best-ranked one (`collapsed` on the result), then the pool is re-ranked by an active-`watch_item` boost and a mild recency decay (half-life 7 days, floor 0.85). The pool is over-fetched to `limit*4`, at most 60.
- **Distinctiveness-weighted keyword search.** Query tokens are weighted by smoothed inverse document frequency over the candidates; the match bonus and miss penalty scale by it; and for a query of three or more tokens a cell failing the count-based coverage gate is still admitted when its matched tokens carry 35% of the query's weight. "What is wrong with the bigquery export" now finds the cell that names BigQuery. One- and two-token name queries stay strict.
- A cell's id is searchable, and a query that is exactly an id returns that cell first. Ids the store generated are not matched as text.
- **`GET /v1/memory/neighbors?id=&top=`**: a cell's nearest cells by embedding and the links among them that mark sub-clusters (a pair is kept only when the two are tighter to each other than to the centre; no similarity threshold). Shared, active cells only; a private or unknown centre is 404.
- **`MemoryStore.SetSourceCollapse` and `SetReranker` land as opt-in Search-time hooks for dual storage's read side — collapsing facts back to the episodes they were drawn from, then a cross-encoder second pass over what's left — while the extraction that actually produces those facts stays external for now** (`internal/xray/memory.go`, new `internal/vectorstore/reranker.go`; `docs/todo/graphiti-comparison-refinement.md` items #2 and #5). Motivated by our own LoCoMo run (same doc): recall@20 on all evidence 53.4%, accuracy 56.5% with gold evidence retrieved vs 8.8% without — the retrieval unit, not the embedder, is the ceiling — and by that run's facts-only arm, which traded +11.2pp temporal for **-8.3pp single-hop** by replacing episodes with facts outright instead of keeping both. Dual storage (episodes kept beside facts) is the fix both our own measurement and Zep's LoCoMo/LongMemEval results point at; this lands the read-side mechanism it needs without committing to an ingest pipeline yet.
  - **`SetSourceCollapse(relation string)`** turns on a new `collapseToSources` step in `Search`: a hit carrying an outbound `ThoughtLink` of `relation` is replaced by the link's target, so ranking happens on the small atomic fact — which embeds and matches better than a 100+-token episode — while the reader gets the source episode back, verbatim detail intact. Dedup is best-first: the best-ranked fact claims its episode's position in the result list, and later facts collapsing to the same episode are dropped rather than duplicating it. A dangling, superseded, or cross-subject target keeps the fact itself rather than losing the hit or leaking across subjects. `""` (the default) is a no-op, verified byte-identical against a store that never calls it, including on/off/on toggling mid-session.
  - **`SetReranker(vectorstore.Reranker)`** adds the cross-encoder second stage item #5 calls for — the one ranker RRF alone can't provide, and the one Zep's winning LoCoMo config actually uses — but only on the fused path; the lexical confident short-circuit never pays for it, so voice keeps its sub-millisecond fast path untouched when the short-circuit is enabled — since the "Changed" entry below, the xray binary fuses by default, so voice searches pay one query embedding per search unless `--search-lexical-shortcircuit` is set. A reranker error or empty result logs a warning and falls back to the incoming RRF order rather than failing the search. New `vectorstore.HTTPReranker` (`NewHTTPReranker(endpoint, model, maxDocChars, timeout)`) speaks the llama.cpp `--reranking` / Jina-shaped `POST /v1/rerank` API (`{model, query, documents, top_n}` → `{results: [{index, relevance_score}]}`), served the same way the embedder is — an in-pod sidecar.
  - **Both channels over-fetch `limit * candidateFanout`** (3 — EverMemOS's own top-30-pooled-to-10-read ratio) whenever either second stage is enabled, so collapse and rerank have a wide enough pool to shrink back down from; with both off, `Search` fetches exactly `limit`, same as before this landed.
  - **`SetCandidateFanout(n)`** makes that over-fetch factor configurable per store: with collapse on, each source episode contributes many fact candidates (on LoCoMo, ~26 facts per 10-turn episode), so the default 3× pool of facts collapses to only ~7 distinct episodes for `limit=20` — a 10× pool is needed to actually fill `limit` with distinct sources, and the cost is in-process HNSW/keyword search, so it's cheap to pay.
  - **`rerank` only sends the cross-encoder the first `limit * rerankFanout` (3) items of the fused/collapsed pool**, not the whole thing — with `SetCandidateFanout(10)` and collapse on, that pool had been a few hundred ~1500-char episode cells per query (~3.6s against one sidecar); the dropped tail was already ranked below the window by fusion and gets truncated to `limit` right after rerank returns anyway.
  - **`SetLinks(id, links)`** is the write side an ingest pipeline needs to use collapse at all: it lets a caller attach `ThoughtLink`s to an ephemeral (non-CR-backed) item, which previously only a CR-backed item could carry, via `cellToItem`.
  - **Not landed yet**: the LLM extraction step itself (splitting an episode into dated atomic facts and linking them back with `SetLinks`) runs in the `xray-recall-evals` harness (`locomo/ingest.go`), not this repo's ingest path. This entry is the substrate the harness's dual-storage arm calls into, not the pipeline itself.
  - **`SetLexicalShortCircuit(on bool)`** makes the lexical confident short-circuit itself switchable: `on=false` forces `Search` to always fuse lexical with semantic by RRF, because the short-circuit's coverage-based confidence check returned a single lexical hit — semantic retrieval skipped entirely — for **41% of LoCoMo questions**, whose long natural-language phrasing trivially covers tokens in a 10-turn episode cell.
  - **Opt-in and default-off**: no existing caller invokes `SetSourceCollapse`, `SetReranker`, or `SetLinks`, so this ships with zero behavior change until something opts in.
  - Tests (`internal/xray/memory_sourcecollapse_test.go`): `TestMemoryStore_SourceCollapse_OffIsByteIdentical`, `TestMemoryStore_SourceCollapse_FactHitReturnsEpisode`, `TestMemoryStore_SourceCollapse_DanglingSourceKeepsFact`, `TestMemoryStore_SourceCollapse_RespectsSubjectVisibility`, `TestMemoryStore_SourceCollapse_FanoutControlsSourceDiversity`, `TestMemoryStore_SetLinks`, `TestMemoryStore_Rerank_NotCalledOnLexicalFastPath`, `TestMemoryStore_rerank_ReordersAndFallsBack`.

### Changed
- **The license is Apache 2.0** (it was MIT), with a `NOTICE` file for third-party software. The patent grant and the contribution terms suit a library that companies embed and run. Releases before this one were published under MIT.
- **The `xray` chart starts with its defaults.** It no longer references Secrets nobody has created (`github-oauth` and `azure-oauth` are opt-in), no longer carries placeholder voice, tracing and GitHub flags, serves MCP with the shared secret on port 8083 and has the ingress off. New `dev` value adds `--dev` for a first look. Without `--dev` the server still refuses to start until a sign-in method and `--public-url` are set; the optional flags are comments in `args`.
- **The module path is `github.com/triageagent-dev/x-ray/v2`.** Go requires the `/v2` suffix for v2 and later, and without it the SDK could not be fetched at any v2 tag. Imports of `api/v1` and the SDK use the new path.
- **One product.** The README, specification and chart descriptions describe X-Ray as an agentic memory substrate for local and Kubernetes-native use, with authored memory (`MemoryCell`) and derived memory (the code graph) behind one MCP endpoint.
- The install snippet registers the MCP server as `xray`.
- CI tests the static build and the CGO build, and renders the `xray-graph` chart.
- **`MemoryCell` is `xray.ai/v1`, and the memory store takes the core's improvements** (ADR-053). The CRD, `api/v1alpha1` → `api/v1`, the chart's CRD and the two chart cells follow; the schema is the Triage core's, so one `memorycells.xray.ai` serves both projects (the core has served `v1` since 2026-09-20, and two CRDs of one name could not coexist in a cluster).
- **A cell is embedded as `kind scope subject title content`, cut to 1800 bytes** (it was `title: content`), so kind and subject steer similarity and a long note no longer fails to index against a local embedder with a 2048-token batch.
- **The `xray` binary now always fuses keyword and semantic Search results by Reciprocal Rank Fusion and applies no semantic score gap, by default** (`cmd/xray/main.go`), flipping the product default while leaving `internal/xray`'s own library defaults untouched. Measured on LoCoMo-10, categories 1-4, same reader/judge (`xray-recall-evals/RESULTS.md`): forcing RRF fusion instead of the lexical confident short-circuit took accuracy 60.6% → 75.0% and recall@all 71.3% → 89.3% (arms C1 → C2) — the short-circuit had been returning a single lexical hit, skipping semantic retrieval entirely, for **41% of questions**. Setting the semantic score gap to 0 separately took raw-turn retrieval accuracy 54.1% → 59.2% (A → A0).
  - **`-semantic-score-gap` default changes 0.02 → 0** (no cutoff); pass `-semantic-score-gap=0.02` to restore the previous cutoff. `internal/xray`'s own default (`defaultSemanticScoreGap` in `internal/vectorstore/memorycellstore.go`) is unchanged at 0.02.
  - **New `-search-lexical-shortcircuit` flag** (default `false`) calls the existing `MemoryStore.SetLexicalShortCircuit(true)` to restore the previous short-circuit behaviour; the library's own default (an unconfigured `MemoryStore`) is still short-circuit-on, so embedding callers of `internal/xray` that never touch this flag or call the setter see no behavior change.

### Fixed
- **Deleted cells stayed in the embedding index.** `Delete` removed the item and its keyword entry but never the vector, so a deleted cell kept taking top-k slots until restart. The index is now marked dirty and rebuilt once before the next read, so a retention sweep costs one rebuild, not one per delete.
- **The per-subject index read its entry map outside the lock** while inserts wrote to it, a concurrent map read and write under load. Reads now hold the lock.
- **A kind-filtered semantic search returned nothing for a kind that was a small share of the corpus**: it fetched `topK*3` nearest cells and dropped the wrong kinds, so a populous kind filled the window. It now exact-scans the kind.
- **A semantic search whose whole top window is rejected on lookup** (every hit a cell deleted or retired elsewhere, still indexed here) returned nothing although other cells qualified; it now ranks every cell exactly. The keyword index also missed any cell created after start-up on another replica.
- **Embedding dimension mismatch.** A vector of another length than the index (a cell embedded by a previous model) corrupted the graph and the query. The store now knows its dimension, refuses both, and the syncer re-embeds a stored vector of the wrong length.
- **The embedder's exact-text cache was unbounded**, holding every query and document embedded for the life of the process. It stops growing at 20,000 entries and search queries have a bounded LRU in front (4096, singleflight).
- Fuzzy matching ran an edit-distance DP against every word; it now skips words whose length rules them out and stops once the answer cannot be within tolerance.
- **The recall linker draws a call edge only where declared evidence points — the repo-wide name guess is gone, and two extractor defects that hid real call sites are fixed** (`internal/recall/parser/{extract_go,helpers_go,walk,types}.go`, `internal/recall/graph/{link,graph}.go`, `internal/recall/mcpserver/{results,mcpserver,readonly,direct}.go`; ADR-043 amended). Found by reviewing `get_graph_impact` on `Registry.UpdateByPaths` against the compiler after a signature change: the blast radius held three `internal/xray/cellsync_test.go` functions that cannot reach it, and missed the two `mcpserver` call sites that broke the build.
  - **The false edges came from the linker's last resort**: an untyped receiver resolved to "the one method of that name anywhere in the repo", so the k8s client's promoted `syncer.Update()` became `engine.Indexer.Update`. Measured across this repo before removal, the same rule put `req.Header.Set` (a `net/http` request) on a local `SecretStore.Set` **56 times** and `rec.Header()` on a test's `flushRecorder.Header` 24 times. It is removed outright: no rule matches on a name across packages any more.
  - **The missed edges were not interface dispatch**, as the review first concluded. The Go extractor dropped the operand of any chained selector, so `d.Resolver.UpdateByPaths(…)` was emitted as a *bare* `UpdateByPaths()` and resolved by the wrong rule (package-local functions). Chained receivers now keep their receiver text and are treated exactly like `x.m()`. (The interface call itself still stays external — interface method specs are not nodes — which is now the documented, consistent answer.)
  - **`pkg.Func()` into the repo's own packages never resolved** ("external by construction"), so not one cross-package call in the repo had an edge. The linker now infers the module path from the repo's own `imports` edges (a strict majority vote over import paths ending in a known package directory; a tie infers nothing) and resolves `engine.NewRegistry()` to the declaration in `internal/recall/engine`. No `go.mod` read, so snapshots built before this resolve too.
  - **What replaced the guess is declared evidence, recorded at parse time.** The extractor binds receivers, parameters, closure parameters, `var`/`:=` locals (including `x, err := f()` and a call into another package, which types nothing but fixes the value's *origin*), and range variables; and records on each node what a chain can be followed on: a struct's field types (`NodeInfo.Fields`, embedded fields under their type name) and a function's single result type (`NodeInfo.Result`, with `(T, error)` read as `T`, and slices/maps/channels as element and key). A call site then carries either its receiver's type and package of origin, or the steps from a bound root (`s.memory.Upsert()` → root `Server`, chain `memory`; `for _, n := range g.Nodes() { n.Touch() }` → chain `Nodes().[]`; `reg := newRegistry(t); reg.Update()` → root the helper, typed by its declared result). The linker walks those steps over `Fields`/`Result`, landing only on exactly-one declarations in the package each step names, and a foreign package ends the walk as external. Every rule is now "the evidence says this package; is there exactly one such declaration there?".
  - **Measured on this repo, same tree**: resolved call edges **3082 → 3284** of ~17.3k, and every one of them now rests on a type, an import or a package. By rule: bare 1939, chain 799, recvType 366, pkg 93, recvPkg 87, by name **0**. `LinkStats.ResolvedByRule` is new so a future regression shows as a shift between rules rather than a silent change in a total. `Indexer.Update` is now reached from `Registry.UpdateByPaths` (map key → field type) and `recall_serve.go`, and from nothing in `internal/xray`.

- **A CGO-free binary can now keep a Markdown/YAML corpus current — it refused every update before** (`internal/recall/engine/`: new `parse_shared.go`, `update.go`, `parseravail_{cgo,nocgo}.go`; `registry_cgo.go` + `registry_nocgo.go` deleted; `parse.go` and `indexer_cgo.go` trimmed. ### Added
- **The voice WebSocket accepts a session token as a subprotocol, and a login can hand that token to a UI on another origin** (`internal/xray/auth.go`, `server.go`, `voice.go`, `github_auth.go`, `azure_auth.go`, `cmd/xray/main.go`, `charts/xray/values.yaml`; `xray-ui/lib/api.ts`, `hooks/use-voice-session.ts`, new `app/auth/callback/page.tsx`). Ported from the sibling `xray-triage-ui`, which already runs this pattern against its controller.
  - **Why a subprotocol at all**: a browser cannot set headers on a WebSocket handshake — `new WebSocket(url, protocols)` is its only channel — so a UI authenticated by bearer token rather than by cookie had *no* way to credential `/v1/voice`. It now sends `bearer, <token>` as the subprotocol list and the server reads it back (`wsBearerToken`), the same technique the Kubernetes API server uses for `kubectl exec`. The server echoes `bearer` on success: RFC 6455 permits selecting none, but then `ws.protocol === ""` and a client cannot tell a server that read the credential from one that ignored it.
  - **The header is honoured ONLY on an actual upgrade request** (`Upgrade: websocket`). Accepting it elsewhere would quietly add a second, far less visible way to authenticate every route in the server; a test asserts the same token on a plain `GET /v1/memory` does not authenticate.
  - **Three carriers, one function.** `sessionFromRequest` replaces three near-identical cookie-then-bearer blocks (`requireSession`, `/v1/auth/me`, `VoiceManager.ServeHTTP`) so they cannot disagree about who the caller is, and so the new carrier lands in all of them at once. Order is cookie → bearer header → subprotocol, and a *stale* cookie falls through to a live bearer token rather than shadowing it — a cross-origin UI can easily hold both.
  - **Login hand-off (`--ui-callback-origins`, empty by default).** X-Ray's cookie is `Secure`, `HttpOnly` and host-only, so it reaches neither a plain-http localhost page nor a UI on another host — and there was no other way to obtain a token, since the cookie is unreadable to JavaScript. A login may now carry `?ui=<origin>`; on success the browser is bounced to `<origin>/auth/callback?token=…` instead of `/`. **The allowlist is not optional and is checked at login, not at the callback**, so an unapproved origin is never bound to a live login and there is no window in which a minted token could be sent to it. Matching is on the normalised scheme+host+port (`resolveUIOrigin`), which is why `https://ui.example.com@evil.example.com` resolves to `evil.example.com` and is rejected. A deployment that never sets the flag behaves exactly as before.
  - **The UI callback page uses `location.replace()`**, not `assign()`: the URL carries the token in its query string, and this keeps it out of history where it would outlive the tab and be recoverable with Back. The token is held in `sessionStorage`, not `localStorage`, so it dies with the tab.
  - **All UI API calls now go through one `apiFetch`** which sets `credentials: "include"` and adds `Authorization: Bearer` when a token is stored — 12 call sites across 6 files, so the two carriers cannot drift apart. It reads the token per call, so a token stored by the hand-off applies without a reload.
  - **Deployed, none of this is used.** The `xray-ui` proxy makes the UI same-origin and the cookie stays the credential — which is stronger precisely because JavaScript cannot read it. This is for `npm run dev` against a remote API, and for `make serve` on plain-http localhost.
  - **Still cookie-only: `/v1/memory/events`.** `EventSource` cannot set headers either, and X-Ray deliberately does not accept a session token in a query string (it would land in access logs), so live SSE updates remain a same-origin-only capability.
  - Tests (`internal/xray/sessioncarrier_test.go`, 9 cases + `xray-ui/__tests__/credentials.test.ts`, 9 cases): subprotocol parsing across header forms (spacing, case, split header lines, sentinel with no token, unrelated protocols), non-upgrade rejection, carrier precedence and stale-cookie fallthrough, the `requireSession` gate end to end, allowlist behaviour including the userinfo case, hand-off off-by-default, and a **real gorilla handshake** asserting `101` + echoed `bearer` + the right user behind the socket, no echo on the cookie path, and `401` for a forged token. UI: storage blocked, header presence/absence, caller-header merge, per-call token read.

- **Hybrid lexical + semantic search for mental maps** (`internal/memmaps/index/lexical.go`, new; `internal/memmaps/index/index.go`). `Index.Search` was pure cosine, which loses queries whose target is phrased in different vocabulary even when the query's exact terms appear repeatedly in it. Measured on the Claude Code memory corpus (`docs/todo/cc-memory-eval.md`): a query naming a CLI and a build step missed the document that repeated those exact terms, losing to a document merely about the same topic. No threshold on a similarity-only signal recovers a term the embedding never encoded — the missing piece is a keyword channel. Ported from triage's `kwindex.go` + `memory_search.go` (ADR-030), keeping its trigram thresholds and scoring weights so the two implementations stay comparable; items here are graph nodes keyed by QN rather than memory cells keyed by id.
  - **Fusion is Reciprocal Rank Fusion (`rrfK=60`), not a weighted score blend**, because the two channels' scores are not comparable: cosine sits in a narrow 0.5-0.8 band while `lexScore` is unbounded integers, so only their ranks can be combined. Both channels over-fetch to `3k` so an item ranked 8th semantically and 1st lexically still surfaces.
  - **The coverage gate cannot demand every query token.** Requiring all of them rejected exactly the documents it should return — "who is supposed to write the implementation code on this project?" carries `supposed`, which the answering memory does not contain even though it holds every other token several times over. The gate is `ceil(2n/3)` for n>2 tokens (all of them for n≤2), with a per-missing-token penalty in `lexScore` keeping full coverage ranked above partial. Stopword filtering is likewise mandatory rather than cosmetic: a question is mostly stopwords, and indexing them makes every document match every query.
  - **Lexical-only hits are stamped with their true cosine** so `Hit.Score` means the same thing regardless of which channel found the result; without it they surface as `Score: 0` and look broken to any caller reading Score as a similarity.
  - **Effect on the 25-question memory eval**: top-5 recall **92% → 100%** with **zero misses** (both previously-unreachable-by-semantics documents now found); in-project top-1 60% → 67%. The trade is real and worth stating: overall top-1 slips 76% → 72%, because fusion promotes lexical candidates that sometimes displace a correct semantic top-1 — right for a caller that reads several results, slightly worse for one that takes only the first. Search cost 7.7ms → 24.5ms p50 (36.5ms p90). Corpus index health (every document queried by its own description) improved to 98.6% rank-1 and **zero unreachable**.
  - The keyword index is rebuilt from the graph at the end of every `Build` path — cold build, snapshot seed, and incremental update alike — so the lexical channel can never describe an older graph than the vectors do. A query with no content-bearing tokens makes the channel abstain rather than vote arbitrarily, leaving pre-hybrid behavior unchanged.

  Tests (`internal/memmaps/index/lexical_test.go`): trigram threshold behavior by token length (short tokens exact, long near-misses rejected), coverage gate table, stopword abstention, re-index posting invalidation, `lexScore` title/coverage ordering, and RRF agreement + cosine preservation + limit.

- **`xray-code serve` warm-seeds its live graph from a snapshot gob instead of re-embedding on every start** (`cmd/memmaps/serve.go`, `seedFromSnapshot`). `serve` already flushed the live graph to `<snapshot-dir>/<label>.graph.gob.gz` periodically and on shutdown, but never read it back: every start re-parsed the repo and re-embedded every node. It now loads that gob through `engine.NewIndexerFromSnapshot`, which pre-populates the text→vector cache and deserializes the persisted HNSW, so the embedder is used only for queries. Measured on a 567-node corpus: **17.5s and 565 embed calls → 22ms and zero**. Mode A stays a live, writable graph — incremental `update` still re-parses and re-embeds only changed files on top of the seeded state, and the next flush rolls those nodes back into the gob (verified end to end: shutdown flush wrote 567 nodes, restart re-seeded them in 61ms).
  - **Seeding is an optimization and never a reason the server won't start**: any mismatch logs and falls back to a cold build. It applies only to a single served repo (matching `snapshotAll`'s own constraint, so flush and seed stay symmetric), requires an exact embedding-fingerprint match (a gob's cached vectors are meaningless under a different model/dims — the same check the registry runs), and requires the gob's recorded repo path to still be the path being served (otherwise the cached file→node mapping describes a different tree and incremental `update` would write into the wrong repo namespace). `-no-seed` forces a cold build.
  - **A seeded graph is exactly as fresh as its gob** — memories written after the last flush are absent until an `update` covers them. That is what the PostToolUse update hook is for.

- **The memory loop: reflection + knowledge passes, ported from a sibling project's mature implementation** (`internal/xray/reflection.go`, new; `internal/xray/memory.go`, `internal/xray/voice.go`, `internal/xray/mcpserver.go`, `cmd/xray/main.go`; ADR-021, deltas in `docs/todo/memory-loop-port-spec.md`). ADR-021 existed as design only — this lands the actual `ReflectionManager`. Two background passes, one goroutine (`runMemoryLoop`): **reflection** distills recent public memory (event/episodic/note/stable_fact/operational_pattern/…, everything except the two config kinds and anything private) into `upsert`/`expire` ops and refreshes the store's situational summary; **knowledge** recomposes a compact digest from `stable_fact`/`operational_pattern` cells (full current set) plus a lookback-bounded window of `recent_change`/`event`/`note`/`episodic` items, injected into every voice session's system prompt (`loadSessionConfig`, `=== KNOWLEDGE DIGEST ===` block) — and never touches the summary, only reflection does.
  - **Loop mechanics mirror the reference exactly**: a buffered `passCh` (2), a `pending [2]bool` coalescing set so both kinds queued while one runs are never lost, reflection always drained before knowledge in one wake-up, a shared 2-minute cooldown between any two passes (blocking wait) plus an independent 1-hour knowledge-only cooldown (skip, not wait). `runPass` is factored out of `runMemoryLoop` (the reference inlines it) specifically so tests can drive cooldown/coalescing synchronously without sleeping for real minutes.
  - **LLM client**: a minimal `reflectionLLM` interface (`Generate(ctx, systemPrompt, userPrompt) (text string, promptTokens, completionTokens int64, err error)`); the production implementation (`genaiReflectionLLM`) reuses `voice.go`'s `newVoiceGenaiClient` for backend selection (Vertex AI via `--gcp-project`, else `--gemini-api-key`) via non-live `Models.GenerateContent`, so the loop and voice sessions can never disagree about which credential is active. Every test uses a fake; none touches a live model or embedder.
  - **Headroom cap + truncated-rewrite guard (spec delta 2, an improvement over the reference)**: every cell body serialized into a pass prompt goes through `headroom.LossyCompress` at 600 chars, flagged `"truncated": true` when cut; the reference only enforces "don't rewrite a truncated cell" by prompt instruction, this port also tracks which ids were sent truncated and has `applyOps` **reject** a content-rewriting upsert against them (log + drop) — `expire` stays allowed. A rewrite composed from a partial view would otherwise corrupt the cell.
  - **Config is not memory (spec delta 3)**: `system_identity`/`system_configuration` are excluded from both passes' prompt context and rejected as `applyOps` targets, whether the op tries to create one fresh or overwrite an existing cell of that kind by id.
  - **No-op discipline (spec delta 4)**: `MemoryStore.SetSummary`/new `SetKnowledgeDigest` skip when the value is unchanged; `applyOps`' upsert path resolves what would actually be written (`resolveUpsertItem`, preserving `Status`/`StaleAfter`/`EventDate`/`Data` from the existing cell so the reflection ops schema — which doesn't carry those fields — can't silently blank them) and compares against the existing cell via the ADR-033 `itemsSemanticallyEqual` helper *before* calling `MemoryStore.Upsert` at all — a repeat pass over a quiet store makes zero `Upsert` calls, not just zero net changes.
  - **Pressure trigger, not per-event (spec delta 5)**: the reference removed direct per-event triggering after it burned ~690K tokens/hour on flapping state; this port never adds it back. Instead a new `--reflection-event-threshold` (default 25, 0 disables) requests a reflection pass once that many new **public** `event`/`episodic` items have been created since the last request — wired via `MemoryStore.SetItemCreateHook`, a plain func field fired once per genuine CREATE (never an update) from inside `upsertWithStaleAfter`, the single choke point every Upsert call already passes through; `ReflectionManager.NoteItemCreated` filters to event/episodic and is the only caller of the hook. It is a **request**, not a bypass — it calls `TriggerReflection`, which enqueues on the same `passCh` every other trigger uses, so `runPass`'s cooldown still gates when the pass actually executes. Other triggers: the interval tick, `build_memory`/`build_knowledge` MCP tools, and voice session end (`VoiceManager.SetReflectionManager`, fired from `ServeHTTP` after a session closes — new public memory may exist worth distilling promptly).
  - **Privacy (spec delta 6)**: pass context is public/instance scope only — `MemoryStore.AllItems` already excludes private-scope and `system_configuration` items, reused as-is for both passes' input. `applyOps` additionally rejects any upsert op carrying `scope: private` outright (the pass had zero private context to legitimately derive one from) and rejects an upsert/expire targeting an *existing* cell that turns out to be private, defense in depth against a hallucinated or injected id.
  - **Usage accounting (spec delta 7)**: pass spend rides the existing per-day usage counters (`AddUserTokens`/`UserTokensToday`, the same machinery ADR-042's per-user voice audio quotas use) under two reserved machine identities, `system:reflection`/`system:knowledge` — visibility only, no budget gate. Falls back to a `(len(systemPrompt)+len(userPrompt))/4` / `len(output)/4` estimate when the provider's `UsageMetadata` reports zero (e.g. a fake in tests, or a provider that omits it).
  - **Single-writer summary/digest (spec delta 8)**: `ReflectionManager.setSummary`/`setDigest` are the sole write paths reflection/knowledge use — direct pass-throughs to the store's setters today, but the one place a future delegate-ownership check (an external System-2 session's heartbeat freshness, mirroring the sibling repo's contract) would land once instead of at every call site.

- **General decay/retention across all memory kinds — "decay by default" is now true substrate-wide** (`internal/xray/memory.go`, `cmd/xray/main.go`; ported/generalized from a sibling project's stale-after discipline). Previously only episodic session memories were ever reaped (`StartEpisodicReaper`, CreatedAt+`--episodic-ttl`); every other kind lived forever. Two pieces:
  - **Decay by default on create.** `MemoryItem` gains a `StaleAfter *time.Time` field mirroring `MemoryCellSpec.StaleAfter` (an existing-but-until-now-unused CR field — no CRD/API change). `Upsert`'s internal implementation (`upsertWithStaleAfter`, called by the unchanged public `Upsert` with a nil deadline so all 39 existing call sites are untouched) stamps a compiled per-kind default deadline on a genuine CREATE with no explicit deadline: `event` 30d, `recent_change` 90d, `note` 90d (`defaultTTLByKind`) — launch defaults pending per-deployment config. Every other kind (`stable_fact`, `operational_pattern`, `watch_item`, `system_configuration`, `system_identity`, `policy`, map-carrying cells, `episodic`, …) is left with a nil `StaleAfter` and never auto-expires. An explicit deadline passed by the caller always wins over the default and is never overwritten. An update never implicitly restamps, extends, or clears the deadline — renewal is only ever an explicit `StaleAfter` set by the writer; a plain content update leaves it exactly as it was, including the "prior" path (an id whose CR exists but was never cached in this pod's `s.items`, e.g. post-restart), which now also preserves the persisted deadline instead of silently dropping it the way the old create-shaped branch would have.
  - **The retention sweep.** `MemoryStore.StartRetentionSweep` (mirrors `StartEpisodicReaper`'s structure exactly: one goroutine, a ticker, exits on ctx cancel, no-op when the interval is ≤0) hard-deletes every item whose `StaleAfter` deadline is in the past, on a new `--retention-sweep-interval` flag (default 1h, 0 disables). It is an internal sweep like the episodic reaper — lists ALL items via the cache reader when available (ignoring scope/subject filtering) and falls back to the in-process map otherwise. Unconditionally exempt regardless of deadline: `system_configuration`, `system_identity`, `policy` (durable/config kinds), any map-carrying cell (identified the same way `CellSyncer.syncMapCell` does — presence of the `Data["graph"]` blob, plus the `kind=="mental_map"` convention those cells are created under), and `episodic` (owned exclusively by the separate episodic reaper's CreatedAt+TTL mechanism — sweeping it here too would double-handle the same kind under two different expiry rules). An item with no `StaleAfter` set never expires. Each expired item goes through the exact same delete path a user-initiated delete uses — `MemoryStore.Delete` (which fires the SSE change event) plus the CR delete via `CellSyncer.Remove` — so downstream behavior (search index removal, live UI updates) is uniform regardless of who initiated it. Logs one summary line per sweep with counts by kind; silent when nothing was swept. Wired in `cmd/xray/main.go` right next to `StartEpisodicReaper`.

- **Memory hub replication surface — `SetHitPublishHook`/`SetChangePublishHook`/`ApplyRemoteHit`/`ApplyRemoteChange` on `Hub`** (`internal/xray/hub.go`, `internal/xray/hub_test.go`; ported from a sibling project's `internal/memoryhub`). `Hub` already had per-user scoped publish (`PublishChangeTo`) but no way for an embedding process to fan a local publish out to peer replicas — the reference solved this for its own package-level singleton hub with two publish hooks plus two remote-apply entry points and a strict split-horizon rule (a hook fires only on a LOCAL publish; a remote apply is delivered to local subscribers but never re-fires the hook, or two replicas would echo the same event back and forth forever). Ported as **methods on `*Hub`** rather than package vars/funcs — this repo's `Hub` is instance-based, not a singleton, so a method surface is the natural (and safer) fit: no risk of one process's hooks leaking into another's construction, which is a real hazard for a package-level singleton but doesn't apply here. `SetHitPublishHook(func(MemoryHitEvent))`/`SetChangePublishHook(func(MemoryChangeEvent))` install (or, passed `nil`, clear) the callback fired at the end of a local `Publish`/`PublishChange`; `ApplyRemoteHit`/`ApplyRemoteChange` deliver a peer-sourced event to this process's own SSE subscribers via the same local-effect path (`applyHitLocal`/`broadcast`) but skip the hook entirely — the intended caller of `Set*Hook` is whatever a future replication transport (a mesh client, a pub/sub bridge) wires in; `ApplyRemote*` is that transport's inbound handler. Unset hooks (the default, and every single-replica deployment today) cost nothing — `Publish`/`PublishChange` behave exactly as before this surface existed.
  - **`PublishChangeTo` deliberately gets no hook**, mirroring the reference's call even though the reasons don't fully carry over: the reference has nothing calling its `PublishChangeTo` yet, so there's nothing to forward; this repo's `Hub` DOES call `PublishChangeTo` today (private notes, in `memory.go`'s upsert/delete paths), but `MemoryChangeEvent` carries no `userHash` on the wire — only the receiving side's subscriber map knows who owns a channel. A peer applying a forwarded private event via `ApplyRemoteChange` would have no owner to scope it to on ITS side and would fall back to broadcasting it to every one of its own subscribers, leaking a private item to users who never should have seen it. Replicating a scoped publish is only safe once the `userHash` travels with the event itself, which is a wire-format change a future private-scope replication feature would need to make first — documented on `SetChangePublishHook` rather than silently omitted.
  - Tests (`internal/xray/hub_test.go`): a local `Publish`/`PublishChange` fires its hook exactly once with the exact event payload; `ApplyRemoteHit`/`ApplyRemoteChange` never fire the hook (while still updating hit counters / broadcasting to subscribers); a remote-applied event reaches subscribed SSE clients identically to a locally-published one; unset hooks change nothing about existing `Publish`/`PublishChange` behavior; a hook cleared with `nil` stops firing.

- **`/authorize` self-heals an unknown MCP OAuth `client_id` instead of bricking re-auth** (`internal/xray/mcpauth.go`, ADR-049 companion): MCP clients (Claude Code among them) cache their `client_id` after the first DCR (`POST /register`) and do **not** re-register when `/authorize` rejects it — so any lost registration (a restart before the registry persisted, an evicted entry past `maxOAuthClients`) bricked re-auth with the opaque `"redirect_uri not registered for client"` error and no client-side recovery path. ### Fixed
- **MCP auth now works across replicas — signing key derived, not random per-pod (ADR-050)**: each replica generated its own RSA MCP JWT signing key at startup (`rsa.GenerateKey` in `newMCPAuthorizer`), so at ≥2 replicas a token signed by one pod was rejected by another (`401`), making `/mcp` flap between "authenticated" and "rejected on reconnect" as the load balancer bounced requests. Sessions (ADR-047) and OAuth clients (ADR-049) were already shared; the signing key was the one piece that wasn't. The key is now an **Ed25519 key derived deterministically from the same OAuth client secrets** that already seed the session HMAC key (`mcpSigningSeed`, label `xray-mcp-signing-v1`) — every replica recomputes the identical key in memory, nothing is persisted. Also removes the "signing key resets on restart" wart for single-replica deployments. Known follow-up: the authorize-code map and rate limiter remain per-replica, so a transient failure is still possible inside the brief `authorize→token` window.

### Fixed
- **Embedder rejected cells over ~512 tokens in an endless reconcile loop**: the local llama.cpp embedder ran without `--ubatch-size`, so the physical batch defaulted to 512. Set the embedder `--ubatch-size` to the per-slot context window (`embedding.sidecar.physicalBatch: 2048`); corrected the misleading `--ctx-size` comment (ubatch, not ctx, is the embedding ceiling).
- **Session greeting silenced under proactive audio**: with proactive audio enabled the model judged the bare greeting (sent as a user turn) as low-signal input and stayed silent at session start. ## [1.19.0] - 2026-06-02

### Added
- **Headroom token compression for the voice `search_memory` path (ADR-038)**: memory-cell content injected into the **Gemini Live** context as `search_memory` tool results was an unbounded text-token surface — full Markdown bodies × up to 10 results per call. Added `internal/headroom`, a dependency-free Go port of two deterministic ideas from [Headroom](https://github.com/chopratejas/headroom): **LossyCompress** (markdown-noise strip — inline-link URLs, code fences, list/heading markers, whitespace — then word-boundary truncation to a char budget; full body stays retrievable by id, the reversible "CCR" contract) and **field factoring** (uniform `kind`/`scope` hoisted to a shared `common` header). Applied **only** to voice `search_memory`; **no result rows are dropped** (every candidate reaches the model for mishear disambiguation). **MCP tools are deliberately not compressed** — they exist to return full context to external agents. Opt-in via `--headroom-content-limit` (default 0 = off; chart `voice.headroomContentLimit` defaults to 500, per-item); `voiceConfig.maxItemContentChars` overrides per voice session. A `headroom compression` debug line logs per-call bytes in/out, tokens saved, and reduction %. Live reduction on the production corpus (short cells) is ~13–23%; 57–80% on long markdown-heavy bodies. Headroom's AdaptiveK (Kneedle/SimHash row-dedup) was prototyped and removed — it omitted zero rows on the real corpus and risked dropping mishear-disambiguation candidates. Supersedes the content-budget portion of ADR-018. New tests: `TestLossyCompress_StripsMarkdownNoise`, `TestLossyCompress_StripsFencedCode`, `TestLossyCompress_TruncatesAtWordBoundary`, `TestLossyCompress_ZeroLimitPassesThrough`, `TestLossyCompress_HardCutsUnbrokenToken`, `TestCompressRows_ZeroConfigIsNoOp`, `TestCompressRows_FactorsConstantFields`, `TestCompressRows_LossyCompressSetsTruncatedFlag`, `TestCompression_RealReduction`, `TestComparison_BeforeAfter`, `TestDefSearchMemory_HeadroomTruncatesContent`.
- **`--log-level=trace`**: the log-level flag handled only debug/info/warn/error — passing `trace` silently fell to info. Added a `trace` case mapping to `zerolog.TraceLevel` for verbose diagnostics (e.g. the semantic score-spread trace), keeping debug output clean.

### Fixed
- **Semantic search returned weak nearest-neighbour padding (absolute-gap relevance cutoff)**: a query that fell through to the semantic path (e.g. "prediction presentation") returned up to `limit` results where only the top was relevant — the rest were nearest-neighbour padding (a person, a project, unrelated blogs). Root cause: the 0.97 *ratio* relevance cutoff existed only per-subject and was discarded by the cross-subject merge (`Search`/`SearchSubject` just sorted + truncated to topK). Worse, a ratio cutoff is the wrong tool here — nomic@256d packs short-query similarities into a narrow anisotropic band (~0.84–0.92 observed across the *whole* corpus), so an unrelated cell scores ~95% of the top by ratio but ~0.04 below it in absolute cosine. Replaced with an **absolute cosine-gap** cutoff applied on the merged cross-subject result (measured against the global top): keep only items within `--semantic-score-gap` (default 0.02; 0 disables; chart `embedding.scoreGap`) of the best hit. `subjectIndex.search` no longer prunes, so the gap is measured against the true global top. "prediction presentation" now returns 1 (was 10). New tests: `TestApplyScoreGap`, `TestSubjectIndex_NoPruning`.
- **New personal notes now appear live via SSE (owner-scoped delivery)**: a created/updated note never populated the UI without a refresh. Private items (`scope=private`) are deliberately not broadcast on the shared `/v1/memory/events` stream (every authenticated client subscribes to it, so broadcasting would leak the note's content), and the hub had no per-user concept — so notes were dropped entirely. The hub is now **user-aware**: each SSE connection registers under its owner's `userHash` (resolved from the session in `/v1/memory/events`), and `Upsert`/`Delete` route private notes via a new `PublishChangeTo(userHash, …)` that reaches only the owner's channels (empty hash → broadcast, for `--dev`). Two latent frontend mismatches that would have kept notes hidden even with delivery are also fixed: the SSE listeners compared `evt.item.subject === userID` (subject is the **hash**, `userID` the **raw** SSO ID — never equal) and matched `kind === "agent_note"` (the backend kind is `note`). New tests: `TestHub_PublishChangeTo_OwnerOnly`, `TestHub_PublishChangeTo_EmptyHashBroadcasts`, `TestMemoryStore_PrivateNoteOwnerScoped`.

### Changed
- **Frontend uses the real `note` kind; synthetic `agent_note` alias removed (revises ADR-037)**: ADR-037 retired the `agent_note` *kind* on the backend but kept the UI synthesizing `kind=agent_note` as a display alias, mapped back to `note` via `KIND_ALIASES` in `category-config.ts`. That alias is now removed — graph nodes, item panel, fetch routing (`fetchMemoryItem`/`/v1/user/notes`), and the subject-hiding header check all key off the canonical `note` kind directly. `KIND_ALIASES` deleted.
